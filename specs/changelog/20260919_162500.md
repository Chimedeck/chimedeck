## Update

`server/extensions/board/api/index.ts` — the new archived-lists route is
registered next to `/archived-cards`.

## New

`GET /api/v1/boards/:boardId/archived-lists` returns a board's archived lists,
mirroring the existing `archived-cards` route.

Archiving a list was previously one-way through the API.
`PATCH /api/v1/lists/:id/archive` toggles `lists.archived`, and
`handleListLists` filters archived rows out:

```ts
const lists = await db<ListRow>('lists')
  .where({ board_id: board.id, archived: false })
```

There is no `?archived=` parameter, no `GET /lists/:id`, and `GET /boards/:id`
includes only active lists. Once archived, a list was invisible to every read
path, while the archive route itself is a toggle that needs the list id to
restore it — so the id could not be recovered. Archived *cards* never had this
problem; `archived-cards` exists precisely so they stay reachable. The UI is
unaffected today because it archives lists it already holds in state, but any
API client (including the MCP server) lost the list permanently.

- `server/extensions/board/api/archived-lists.ts` — `handleGetArchivedLists`,
  built on the same middleware chain as `archived-cards.ts`:
  `applyBoardVisibility` first, then `requireWorkspaceMembership` for non-PUBLIC
  boards. Returns `{ data: [...] }` ordered by `position`, with the same list
  fields the active-lists route returns.
- `server/extensions/board/api/__tests__/archivedLists.test.ts` and
  `__tests__/fixtures/archivedLists.ts` — subprocess fixture following the
  `queryWorkspaceSearch` pattern. Covers: only archived lists from the requested
  board, an empty result as `[]`, a visibility failure short-circuiting before
  any query, the membership gate on a non-PUBLIC board, and a PUBLIC board
  skipping that gate. Verified to fail when the `archived: true` filter is
  flipped.

Compatibility: purely additive — no existing route, response shape or query
changes. Access rules are identical to `archived-cards`, so a board that is
readable today exposes nothing new beyond its own archived list titles.
Restoring a list still goes through `PATCH /api/v1/lists/:id/archive`, which
toggles; this route just makes the id discoverable again.

## Technical Debt

None.

## What Should Be Done Next

- `PATCH /api/v1/lists/:id/archive` is a toggle rather than an explicit
  set-state route. An `{ archived: boolean }` body would make restore
  idempotent and remove the need to know the current state.
- Consider surfacing archived lists in the board UI, the way archived cards
  already are, so the new route has a client.
