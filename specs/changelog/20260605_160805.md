## Update
- The board **GitHub URL** setting now accepts plain repository clone URLs in addition to the existing GitHub Project URLs. Three shapes are accepted end-to-end:
  1. Project URL — `https://github.com/(orgs|users)/<owner>/projects/<n>` (existing)
  2. HTTPS repo URL — `https://github.com/<owner>/<repo>(.git)?` (new)
  3. SSH clone URL — `git@github.com:<owner>/<repo>(.git)?` (new)
  Both new shapes are normalised server-side to the canonical `https://github.com/<owner>/<repo>` form before being stored, so the audit log + cache keys remain stable regardless of the input flavour.
- The board settings dialog now labels the field **"GitHub URL"** (label/placeholder/helper/error copy), and the input is `type="text"` with `inputMode="url"` so SSH clone URLs aren't rejected by the browser's native URL validator. Our own regex runs on blur/save.

## New
- Extended `normalizeGithubProjectUrl` in `server/extensions/board/mods/githubProjectUrl.ts` to recognise the two new URL shapes. Introduced two new scope values (`repo-https`, `repo-ssh`) on `GithubProjectScope` / `GithubProjectReference`; for these scopes `projectNumber` is `0` so the existing reference shape stays stable. Owner and repo names are validated against GitHub's actual rules (no leading/trailing dots, no `.git` / `..` repo names, owner limited to 39 alphanumeric+hyphen chars).
- Added a dedicated `parseSshCloneUrl` parser for `git@github.com:owner/repo(.git)?` (URL `new URL()` doesn't accept these).
- Downstream consumers (`downloadRepositoryFromProjectUrl`, `githubApp.toInstallationKey`, `githubApp.toInstallationPath`) now treat `repo-https` and `repo-ssh` the same as the existing `repo` scope: the installation lookup is per-repository, and the checkout URL is canonical HTTPS.
- Added 21 unit tests in `server/extensions/board/mods/__tests__/githubProjectUrl.test.ts` covering: project-URL shapes (org/user/repo), HTTPS repo URLs (with/without `.git`/trailing slash, invalid owners, reserved names), SSH clone URLs (with/without `.git`, foreign-host rejection), and `toGithubProjectAuditValue` (incl. null/undefined input).
- Added 2 new tests in `downloadRepositoryFromProjectUrl.test.ts` confirming the new shapes reach the git checkout layer and use the canonical HTTPS remote URL.
- Added 3 new client-side tests in `BoardSettings.githubProjectUrl.test.tsx` covering the new shapes (`HTTPS repo URL accepted`, `SSH clone URL accepted`, `unrelated URL still rejected`).

## Technical Debt
- The DB column name is still `github_project_url` even though the field is now used for both project and repository URLs. Renaming would require a migration + a large cross-codebase find/replace, and the field is still semantically the "linked GitHub reference" for the board. Deferred.
- The client-side test suite has pre-existing failures (10 tests in the same file) caused by the loading-state component not rendering the input during the initial `getBoardIntegrations` fetch, so `screen.getByRole('textbox')` fails on synchronous assertions. This is independent of the URL-shape work — the 3 new tests I added hit the same pattern and fail for the same root cause, so they're not a regression. Worth fixing in a follow-up by wrapping the initial state assertions in `findBy` queries.
- `specs.test.ts` has 2 pre-existing failures (env expects `github-app[bot]` but the local `.env` sets `chimedeck-bot`). Not related to this change.

## What Should Be Done Next
- When a board has a repo-shaped URL configured, the existing Documentation tab (Sprint 170) will eventually need to clone the repo directly rather than looking up `orgs/.../projects/N`. The current `downloadRepositoryFromProjectUrl` already supports that path, but `BoardPage.tsx`'s `githubProjectUrl` gate and the `specs/load.ts` cache key should be reviewed to ensure repo-shaped URLs are treated as "link is valid" for showing the Documentation tab.
- Consider a small UX hint next to the field: a tiny example chip that, when clicked, fills the input with a known-good example URL.
- Consider validating that the `repo-https` / `repo-ssh` URLs are actually accessible to the GitHub App installation (e.g. a one-time HEAD probe on save) and surface a friendlier error if the installation doesn't have access to that repository.
