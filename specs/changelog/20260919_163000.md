## Update

A board must always keep at least one ADMIN. Two routes could break that and
did not check: `PUT /1/boards/:id/members/:idMember` and
`DELETE /1/boards/:id/members/:idMember` in the Trello-compatibility adapter.

`members/update.ts` and `members/remove.ts` both refuse to demote or remove a
board's only ADMIN, returning `409 last-board-admin`. The Trello-compat adapter
reaches the same table with no such check:

```ts
// PUT /1/boards/:id/members/:idMember
const boardRole = memberType === 'admin' ? 'ADMIN' : 'MEMBER';
...
await db('board_members').where({ board_id: board.id, user_id: idMember })
  .update({ role: boardRole, ... });

// DELETE /1/boards/:id/members/:idMember
await db('board_members').where({ board_id: board.id, user_id: idMember }).delete();
```

`memberType` defaults to `'normal'` when the parameter is absent, so a bare
`PUT .../members/:id` demotes the target to MEMBER. Both routes are gated only
by `canWriteBoard`, which the last admin satisfies for their own board — so that
admin could demote or remove themselves and leave the board with zero admins.
`trelloCompatRouter` is mounted unconditionally in `server/index.ts`, behind no
feature flag. Once a board has no ADMIN, `members/update.ts` cannot promote
anyone back: promotion requires workspace ADMIN+ or an existing board admin.

The check that `members/update.ts` and `members/remove.ts` each carried inline
now lives in one helper used by all four routes:

- `server/extensions/board/api/members/update.ts` and
  `server/extensions/board/api/members/remove.ts` — the inline copies call the
  helper. Same status, same error name, same messages.
- `server/extensions/trelloCompat/api/boards/index.ts` — both member routes call
  the helper before writing and return `409` via `trelloError`.

Compatibility: the native routes see no behaviour change — identical statuses,
error names and messages, just sourced from one place. On the Trello-compat
routes, a client that previously demoted or removed a board's last admin now
gets `409`; that call produced an unadministerable board, so no legitimate
workflow depended on it.

This change is 5 source files, above the "≤ 2 files" manual-contribution
guidance in CONTRIBUTING.md. Two are the substantive fix (the adapter routes and
the new helper); three are the extraction that avoids a third and fourth copy of
the same check. Splitting it would leave the duplication in place.

## New

- `server/extensions/board/api/members/lastAdmin.ts` —
  `wouldRemoveLastBoardAdmin(boardId, userId, nextRole)`, where `nextRole` is
  `null` for removal, plus the two shared message constants. Returns false when
  the member does not exist, is not an ADMIN, or stays one; otherwise it counts
  the board's admins.
- `server/extensions/board/api/members/__tests__/lastAdmin.test.ts` and
  `__tests__/fixtures/lastAdmin.ts` — helper semantics (sole admin vs. second
  admin, role kept, non-admin target, unknown member) and the native
  PATCH/DELETE routes still returning `409`.
- `server/extensions/trelloCompat/tests/unit/lastBoardAdmin.test.ts` and
  `tests/unit/fixtures/lastBoardAdmin.ts` — the two adapter routes refuse the
  last admin and still succeed while a second admin remains. Verified to fail
  when the new guards are removed.

Both suites use the subprocess fixture pattern from `queryWorkspaceSearch`.

## Technical Debt

The invariant is enforced in application code on four routes rather than by the
database, so a fifth writer to `board_members` would have to remember to call
the helper. A partial unique index or trigger asserting "at least one ADMIN per
board" would make it structural.

## What Should Be Done Next

- Audit any future writer to `board_members` against this helper; the four
  current routes are covered.
- Consider whether the Trello-compat adapter should reuse the native handlers
  outright instead of issuing its own queries — the duplication here is what
  allowed the two routes to drift from the invariant in the first place.
