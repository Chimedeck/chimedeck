## Update
- Fixed a silent-failure bug in JWT/GitHub-App key decoding that caused a confusing `500` with a stack-trace-only error message on the `/api/v1/auth/token` login endpoint. The deep error was `Uint8Array.fromBase64 requires a valid base64 string` — thrown from inside `jose`/Bun's `KeyObject` constructor when a malformed `JWT_PRIVATE_KEY` or `JWT_PUBLIC_KEY` env var was loaded.

## Root Cause
`server/config/env.ts` previously used `Buffer.from(raw, 'base64').toString('utf-8')` to decode base64-encoded PEM keys. `Buffer.from(str, 'base64')` is **lenient** — it silently discards invalid characters like stray `=`, whitespace, or truncated bytes. The resulting string *looked* like a valid PEM and got passed to `jose.importPKCS8`, which then crashed when Bun's strict `Uint8Array.fromBase64` rejected the corrupted inner DER block. The deep stack trace leaked to the client as a generic 500 with no actionable hint about which env var to fix.

## New
- Extracted the PEM/base64 decoder into `server/config/decodeKey.ts` and re-exported it from `env.ts`. The new decoder:
  1. Strips whitespace before validating.
  2. Rejects input that isn't a base64 character set with a message that names the env var (`JWT_PRIVATE_KEY contains invalid base64 characters…`).
  3. Rejects base64 that decodes to something that isn't a PEM block (`…decoded value does not look like a PEM block…`).
  Errors fire at server startup instead of on first login.
- Added 7 unit tests in `server/config/__tests__/decodeKey.test.ts` covering: empty input, raw PEM pass-through, base64 round-trip, whitespace tolerance, invalid-base64 rejection, non-PEM decoded content, and "names the offending env var" guarantee.
- Added a new `AccessTokenKeyError` type in `server/extensions/auth/mods/token/issue.ts`. `importPKCS8` is now wrapped in a try/catch that re-throws as `AccessTokenKeyError` with a clear remediation message ("re-run the openssl keygen step…").
- `handleLogin` in `server/extensions/auth/api/login.ts` catches the new error and returns a structured `500 { error: { code: 'auth-server-misconfigured', message: '…see server logs.' } }` plus a `console.error` with the actionable detail. The deep stack trace no longer reaches the client.
- `importSPKI` in `verify.ts` is now wrapped symmetrically — a malformed public key just denies the token (returns `null`) rather than crashing the verify path.

## Technical Debt
- The fix is in `decodeKey` + the two `token/issue|verify` files. The same decoder is also used for `GITHUB_APP_PRIVATE_KEY` (Sprint 123), which now also benefits from the strict validation. The GitHub App tests that load real keys (if any are added later) should still pass because valid base64-of-PEM still round-trips correctly.
- The global `handleUnhandledError` middleware in `server/common/middlewares/errorHandler.ts` was not changed. Auth-specific errors are caught before reaching it, so the leaked-message problem only existed for the auth path. If other call sites encounter similar jose/Bun failures in the future, consider extracting the same `try/catch` + typed-error pattern there too.

## What Should Be Done Next
- Consider running `decodeKey` once at startup (instead of every env access) and validating ALL three env vars (`JWT_PRIVATE_KEY`, `JWT_PUBLIC_KEY`, `GITHUB_APP_PRIVATE_KEY`) eagerly. Today the error only fires when each key is first read by the consuming code, which means a malformed `JWT_PRIVATE_KEY` doesn't fail boot — it fails the first login. Eager validation would surface all key problems at startup.
- Add a startup smoke test that decodes a known-good and a known-bad env to ensure the decoder's error messages stay actionable.
- Audit other env vars in `server/config/env.ts` for similar lenient-decoding patterns (`parseInt` with `?? '0'` is fine; `?? ''` for things later validated as base64 is the actual risk class).
